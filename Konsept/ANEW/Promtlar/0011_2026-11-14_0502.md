### Kimlik doğrulama (AuthN) — H-1
| Konu | Öneri | Gerekçe |
|---|---|---|
| Login yöntemi | **E-posta + şifre**, ASP.NET Core Identity ile (Identity modülünde). 5 hatalı denemede geçici kilit. | Kararı bana bıraktın. En sade ve kendi kendine yeten yöntem bu. Google ile giriş gibi seçenekler ileride eklenebilir. |
| Web ↔ API | API kısa ömürlü bir **JWT** (15 dk) ve dönen bir **refresh token** veriyor (DB'de hash'li). Web bunları **sunucu tarafında, şifreli, HttpOnly bir cookie** içinde tutuyor. | Tarayıcı token'ı hiç görmüyor. Bu sayede XSS ile token çalınamıyor. |
| Ajan girişi | **Cihaz eşleştirme:** ajan bir kod gösterir, kullanıcı web'de onaylar. Ajan kendi refresh token'ını alır. | Ajana şifre yazdırılmıyor. |
| Çıkış (BR-14) | Web'den çıkış o kullanıcının **tüm oturumlarını**, ajan dahil, iptal eder. Sunucu ajanın SignalR bağlantısını kapatır. | Senin kuralın. |
| Ban (BR-13) | Banlanan kullanıcının tüm token'ları anında iptal edilir. | — |

### Yetkilendirme (AuthZ)
- **Varsayılan: kapalı.** Her API endpoint'i giriş ister; yalnızca login ve kayıt gibi açıkça işaretlenmiş uçlar açıktır.
- **Yetki tabanlı politikalar:** örneğin `admin.panel`, `publish.use`, `model.use:<model>`. Roller bu yetkilerin paketleridir.
- **Asıl yetki kontrolü API'de.** Web yetkisiz butonları gizler ama karar her zaman API'nindir.
- **Sahiplik (BR-1):** EF global query filter ile her sorgu otomatik olarak `UserId`'ye göre filtrelenir. Başka kullanıcının verisi sorguya hiç gelmez.
- **Hız sınırı:** login ve üretim uçlarında rate limiting.

### Girdi ve çıktı
- Her API isteği FluentValidation'dan geçer.
- Razor otomatik encode eder. **Kullanıcı ya da LLM içeriği için `Html.Raw` yasak.**
- **LLM çıktısı güvenilmeyen veri** muamelesi görür. Konsept metni ekranda düz metin olarak gösterilir. İnternetten araştırılan içerik promptlarda "veri" olarak işaretlenir, talimat olarak değil (prompt injection önlemi).
- MVC Ajax POST'larında **anti-forgery token** (CSRF koruması) gönderilir.
- Güvenlik başlıkları: CSP (inline script yasak; K-7 ile uyumlu), `X-Content-Type-Options`, `frame-ancestors`.
- Hata mesajlarında iç detay yok (Konu 6'daki ProblemDetails kuralı).

### Gizli bilgiler — H-2
- API key'ler **ASP.NET Data Protection** ile şifreli tutulur. Data Protection anahtarları Pi'de kalıcı bir klasörde durur ve **yedeklenir**. Bu anahtarlar kaybolursa kullanıcıların kayıtlı tüm API key'leri çözülemez hale gelir.
- Üretim ortamındaki gizli bilgiler (DB şifresi vb.) Pi'de ortam değişkeni ya da systemd `EnvironmentFile` ile verilir, repoda bulunmaz. Repoda yalnızca `.env.example` olur.
- Loglarda şifre hiç, API key maskeli olarak yer alır.

### Kullanıcı bilgisayarı — H-4
- LLM'in ürettiği kod **yalnızca kendi iş klasörüne erişebilen, ağ erişimi kapalı** bir süreçte render edilir. Yöntem (Windows Job Object/AppContainer, Node permission model…) video motoru araştırma raporunda kesinleşecek.
- Ajan güncellemeleri **imza ya da hash doğrulamasından** geçmeden kurulmaz.
- Ajan yalnızca kimliği doğrulanmış API bağlantısından gelen komutları çalıştırır.

### Bağımlılık politikası

- Kontrol listesi:

### Güvenliği etkileyen 1 açık nokta
**Site yalnızca yerel ağdan mı erişilecek, yoksa internete de açılacak mı?** Önerim: **internete açılacakmış gibi tasarlamak**, yani HTTPS zorunlu, Pi'de TLS sonlandıran bir reverse proxy (Caddy) ile. *Gerekçe:* çok kullanıcılı bir sistem, kayıt ve banlama zaten başkalarının da kullanacağını gösteriyor. Güvenli cookie'ler de HTTPS istiyor. Baştan HTTPS ile kurmak, sonradan geçmekten çok daha ucuz. Yalnızca LAN'da kalacaksa da aynı yapı yerel bir sertifikayla çalışır.

**Karar:** Bu güvenlik kurallarını ve açık noktadaki önerimi (HTTPS zorunlu, internete açılacakmış gibi tasarım) kabul ediyor musun? Değiştirmek istediğin madde varsa yazman yeterli.
