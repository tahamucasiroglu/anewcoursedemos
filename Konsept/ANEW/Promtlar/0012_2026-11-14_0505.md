## Adım 2 — INTERVIEW · Konu 10/11: Git kuralları

Bu konu `docs/git.md`'ye yazılacak. Burada ANEW'in varsayılanlarıyla senin çalışma düzenin arasında **önemli bir çakışma** var, önce onu açıklayayım:

> ANEW varsayılan olarak her işi ayrı bir branch'te yapıp sonra merge ediyor (`feature/…`, bootstrap için `chore/bootstrap`). Ama repo kökü olan `anewcoursedemos`'ta **aynı çalışma klasörünü başka oturumlar da aynı anda kullanıyor**, örneğin `TAHA` tarafı. Ben burada `git checkout feature/…` yaparsam bütün repo o branch'e geçer. Paralel çalışan diğer oturum o an commit alırsa, commit'i **benim branch'ime düşer**. Commit'ler yanlış yere gider, iş karışır.

**Önerdiğim git kuralları:**

| Konu | Öneri | Gerekçe |
|---|---|---|
| Branch | **Doğrudan `main` üzerinde çalışmak, hiç branch değiştirmemek.** ANEW'in "default branch'e doğrudan commit yasak" kuralı bilinçli olarak gevşetiliyor ve gerekçesi `docs/git.md`'ye yazılıyor. | Paralel oturumlarla ortak bir çalışma klasöründe branch değiştirmenin tek güvenli alternatifi bu. Git geçmişin de zaten bu şekilde (`main`). |
| Bootstrap commit'i | Bu nedenle bootstrap çıktısı da `chore/bootstrap` yerine **`main`'e** commit'lenecek. | ANEW'in bootstrap kuralından bilinçli bir sapma; GENERATE adımında raporda belirtilecek. |
| Ne commit'lenir | **Yalnızca `Konsept/ANEW/` altındaki dosyalar**, her zaman isim vererek: `git commit -- Konsept/ANEW/<yollar>`. `git add -A`, `git add .` ya da `commit -a` asla kullanılmaz. | Senin kuralın; ANEW'in "yalnızca adı verilen yolları commit'le" kuralıyla da birebir aynı. Başka bir oturumun stage ettiği dosyalar commit'e karışmaz. |
| Eşzamanlı commit | Commit'ten önce `git status` kontrol edilir. `.git/index.lock` varsa (başka biri commit alıyor demek) beklenip tekrar denenir. **Lock dosyası asla silinmez.** | Senin uyardığın "iki kişi aynı anda commit" durumunun güvenli çözümü bu. |
| Push | **Yok.** Remote da tanımlı değil. | Senin kuralın. |
| Commit mesajı | Türkçe, başında İngilizce tür öneki ve plan referansı: `feat(concepts): konu önerisi üretimi [plan 0003/2]`. Review düzeltmeleri `[plan 0003/fix-1]` şeklinde. | Konu 6'daki kararın ve ANEW standardı. |
| Commit onayı | Commit mesajlarını ben yazarım. Onaylanmış bir plan, kendi adım commit'lerini kapsar; her commit için ayrıca sorulmaz. Ship commit'i SHIP onayıyla alınır. | ANEW kuralı, lite ve strict modda aynı. |
| Prompt kayıtları | `Promtlar/` dosyaları, yapılan işin commit'ine dahil edilir. İş commit'i yoksa ayrı bir `docs(promtlar): …` commit'i alınır. | Kayıtlar kaybolmasın, geçmişte iş ile birlikte görünsün. |
| PR | Remote olmadığı için PR yok. PR'ın yerini ANEW'in bağımsız review'ı (ayrı, salt-okunur reviewer) ve senin SHIP onayın tutuyor. | — |
| Versiyon etiketi | Pi'ye her gönderimde bir etiket: `anew-konsept/v0.1.3`. | Repoda başka projeler de var; önek, etiketlerin karışmasını önlüyor. |
| Yasaklar (değişmiyor) | Force push, geçmişi yeniden yazma. Geri alma yalnızca `git revert` ile. | ANEW kuralı. |
